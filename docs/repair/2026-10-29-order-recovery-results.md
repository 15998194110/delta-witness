## 同一订单的数据权威

| 数据 | 职责与权威 |
|---|---|
| `settlements/` | 原授权的结算占位及结果；首次占位绑定订单 ID、请求、付款、凭据摘要、权限、创建和到期时间。未知结果不允许再次结算。facilitator confirmed 不等于 Treasury received。 |
| `orders/` | 不可覆盖的恢复索引；仅保存凭据摘要和原请求绑定。必须与原结算日志交叉校验，索引本身不能证明付款。 |
| `fulfillments/` | 原始交付草稿、决策完整摘要、状态和 ETag 条件写。恢复只能提交原草稿，不能重拍或重新计算 Guard 结论。 |
| 私有 proof artifacts | 原 HTML、Markdown、PNG 和 manifest；原始内容与哈希/时间保持不变。 |
| JS 调用方持久存储 | 原订单 ID、原服务 origin、请求摘要、私有恢复凭据与签名前状态；不是服务端结算账本。需要调用方实现真正持久、原子的 CAS。 |
| D1 / 漏斗与经济指标 | 分析信息，不能覆盖订单、结算、交付或链上到账事实。 |

## 实际修改

- Core 增加 `GET /v1/orders/:id`、`POST /v1/orders/:id/recover`、`GET /v1/orders/:id/artifacts/:artifact`。查单、恢复及导出均不调用 signer、facilitator settlement 或 Browser。
- Capture/Preflight 可携带成对的 UUIDv4 订单 ID 和 32 字节随机恢复凭据。服务端只存凭据摘要。凭据不放 URL，不从公开付款签名补发，不以公开 proof ID 授权下载。
- `ORDER_RECOVERY_TTL_SECONDS` 必须显式配置为 60–604800 秒；未配置时选用新凭据的请求在 402 前拒绝。没有设置生产默认值或新增保留承诺。未携带新凭据的旧购买流程继续兼容；Pilot 暂不接受该选项。
- 当前锁定 x402 upfront 依赖会跳过独立 verify；新凭据路径现在明确验证后才预留/绑定。无效签名不创建订单、结算日志或 Browser 工作。
- 同一授权争用多个订单只允许原结算占位的订单获得恢复权限；同一订单变更请求、付款 nonce 或凭据不会开启新支付。历史已结算/交付授权不能被重新登记成新恢复凭据。
- 查单、恢复和导出共用 `order-storage.ts`，限制元数据、manifest、文件字节及整个操作 15 秒期限。凭据在交付前重新检查；迟到响应流被取消。已发出的条件写可能在超时响应后完成，后续查单读取实际状态，不重新收费。
- 导出仅返回已验证、已完成订单的原始四类文件，以私有附件响应，保留 sandbox、nosniff、no-store；公共 verifier 仍不提供原始文件。
- JS 新增 `prepareOrder`、`executeOrder`、`recoverOrder`。签名前原子持久化 `signing_started`，重启和并发重入只查原单。404、过期、存储异常和结算未知都不解释为“未付款”。首次合法授权购买仍自动执行。
- 新原始响应摘要绑定完整 Guard 决策、route、请求摘要及 fulfillment identity。新订单不能通过删除摘要降级到旧记录，包括不带恢复凭据的原付款头重放和 processing 草稿恢复。旧无结构付款头的已完成记录仍可按原历史路径读取。
- OpenAPI 增加私有恢复/导出契约，明确非收费、凭据范围与未配置状态，且始终将 `treasury_received` 留为未确认。
