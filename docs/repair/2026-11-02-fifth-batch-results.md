唯一需求基线仍为 v1.1「整体稳定性约束版」。本批从报告提交 `90010302948a13f7ffa01824000a2ebba65b87a1` 继续，实际代码提交为 `08487e6ece27894a83d8b3843beb433a2bd48809`。旧四批证据保持原样；本批结果以 `validation-evidence-batch5.json` 和 `acceptance-status-batch5.json` 为准。没有生产发布、迁移、真实支付/删除、客户外联或任务启停。

## 为什么此前没有闭合

上一轮过早以“本地候选通过”作为阶段终点，仍有可以继续实现的本地缺口。它们不能一概归因于没有用户授权或缺少线上测试。复查还发现 D06 的范围被扩大：原文只要求“到期/撤销/超范围凭据失败；更新授权不会重复收费”，没有要求丢失所有原始身份后也能找回。把后者列为这条验收的前置阻塞不正确。

原经营脚本尚未统一采用协调协议、真实 provider reader 尚未实现或接入，也是真实的集成未完成。生产操作的授权边界是另一件事，不能替尚未实现的本地代码作解释。

## 这次实际补修

原有效 capability 现在可以为原订单签发/轮换短期、仅限导出的派生凭据。原 root 摘要、scope、起止时间、结算权威、付款 journal、履约和 proof 均不改；仅在原订单索引上通过 ETag CAS 更新一个授权子记录。原凭据过期或被撤销时不补发原身份；派生凭据不能查单、恢复、管理授权或购买。原订单收费不变。

`GET/POST /v1/orders/:id/export-authorization` 使用原私有 header。调用方先保存 operation/token/expected generation，再进行一次不带付款的 POST；结果未知后保留原操作并 GET 读回。旧 operation 不能覆盖新代次，轮换使旧派生 token 失效。TTL 受 60–3600 秒技术范围、原 root 到期和原 raw retention 同时限制。响应只给元数据，不回显 token 或摘要。OpenAPI、JS/Python SDK 与文档已接上同一 Core wire；Base/MCP 沿用共享 JS 字节和原持久单元，无另建付款逻辑。

经营协调器补上了实际历史字段识别：`last_sent_message_id`、`superseded_message_id`、`bounce_message_id`、`failed_recipient`，以及分发记录的 `endpoint` / `url`。此前漏认这些字段可能允许另一 action_id 对旧目标再次准备首联。新增回归在修复前 8 失败/1 通过，修复后连同旧协调测试 19 项通过；原 unknown、抑制、关闭状态和锁策略保持。该补丁没有把旧 writer 自动接入，也没有增加发送功能。

## 当前状态与真实剩余项

D06-T03 现在是 local_tested，限定于仍有效原身份下的导出授权更新。108 场景当前为：63 local_tested、36 partial_local、8 not_run_external、1 blocked_contract；8 个系统门禁仍为 partial_local。原场景/标准没有删除或改写。

- **仍有本地集成未完成**：旧经营 writer、pipeline/sprint 多文件中断恢复、真实 SENT/platform reader 尚未统一接入。当前协调器只约束遵守同协议的 writer。这些不能写成“代码全部完成，只差上线”。
- **确实需要外部条件**：合作方字段原始合同、真实平台计费/结算读回、现行账号和任务授权、真实上线/迁移/回退及独立客户交易证据。本次本地范围不提供这些事实。
- **历史证据缺失**：原历史候选中一个文件的原始字节仍无法与旧 manifest 核实，D01 继续部分完成；保留原件，不修改旧 SHA 使其通过。
- **额外功能边界**：丢失全部原 capability 后找回身份、延长原保留期、退款/赔付政策没有被本次导出授权更新暗中补造；前者不再被误用为 D06 原标准的阻塞条件。

原外层/嵌套仓库 HEAD 与改动数量、原经营四份文件哈希再次核对不变。当前候选还没有线上验收或收入闭环证据。后续工作必须继续区分本地实现、隔离测试、实际接入、发布和外部实证。
